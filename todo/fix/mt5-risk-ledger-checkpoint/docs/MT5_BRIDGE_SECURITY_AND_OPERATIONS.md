# ATOS MetaTrader 5 Bridge — Security and Operations

## Scope

The MT5 bridge is a local, read-only broker telemetry and market-data channel. The desktop application owns the Rust TCP listener. `MQL5/Experts/ATOS_Bridge.mq5` is an MQL5 Expert Advisor that reports account state, open positions, active pending orders, multi-symbol ticks, and completed OHLC bars for configured timeframes.

This bridge does **not** submit, amend, close, or cancel orders. It does not make AI output executable. It does not authorize live trading. The terminal's trading-permission flags are observed for diagnostics only.

No sample account, synthetic quote, fabricated position, mock order, or fallback broker response is used. If a required account snapshot or configured history read fails, the EA withholds the complete frame rather than advancing local cursors for data that was not durably acknowledged.

## Trust boundary

- The Rust listener binds only to `127.0.0.1:47650` and permits one active terminal session.
- The EA accepts only the exact host `127.0.0.1`; remote MT5 terminals are not supported.
- A 256-bit pairing token is generated from two UUIDv4 values and stored in the operating-system credential store through `keyring`. If the credential store is unavailable, the listener remains disabled; there is no plaintext-file fallback.
- The pairing token is sent over loopback TCP and is **not encrypted in transit**. This transport is intended for the same trusted computer only. Do not forward the port, tunnel it to another machine, or run untrusted local software while the credential is exposed.
- The operator must paste the pairing token into the EA input. Treat the EA input configuration and terminal data directory as secret-bearing local state.
- Protocol v6 uses bounded newline-delimited JSON, strict field decoding, a timestamp window, nonce replay tracking, per-EA-session sequence receipts, and exact-payload replay detection. The frame limit is 2 MiB; the account snapshot still refuses to truncate more than 200 open positions or 200 active pending orders. After authentication, every frame is bound to the authenticated account login/server and the exact symbol/timeframe subscription; out-of-scope frames are rejected before storage.
- Authentication and telemetry use bounded socket timeouts. Account heartbeat freshness is 5 seconds; the primary quote freshness is evaluated separately at 60 seconds.

## Data contract

Every frame carries an account snapshot with complete bounded open-position and active pending-order inventories, per-item stop-loss risk states, broker margin/stop-out policy, a `marketData` batch, and a `sessionSchedules` collection. Protocol v6 requires exactly one complete seven-day broker-reported trading calendar for every authenticated watched symbol on initial pairing, reconnect, and each scheduled refresh. Unchanged heartbeats may omit the calendar payload only when the durable store already has a valid, fresh calendar for every authenticated symbol; the receiver rejects missing initial calendars, incomplete updates, stale retained calendars, and out-of-scope symbols before commit.

- `ticks`: symbol, broker timestamp in milliseconds, bid, ask, last, integer volume, real volume, and MQL5 tick flags.
- `bars`: broker symbol, timeframe code, bar-open timestamp in milliseconds, OHLC, tick volume, spread, real volume, and an explicit `closed=true` marker.
- `pendingOrders`: complete active pending-order inventory (bounded at 200) with ticket, broker symbol, MQL5 order type/state, initial and remaining volume, entry/current/stop-limit prices, SL/TP, millisecond setup time, expiration time, magic identifier, and a broker-calculated stop-risk state/value. `positions` carries the same stop-risk state/value for each open position. The EA refreshes each selected order before reading its properties.
- Any failed selection, malformed order, duplicate ticket, or over-cap inventory withholds the complete frame.
- MT5 inventory enumeration is fenced after serialization. The EA re-checks ticket cardinality/set and risk-bearing position/order fields (type, volume, current mark, state, activation/entry price, stop-limit price, and SL); it withholds the frame on any change. Immediately before every frame is transmitted, it also rechecks account balance/equity/credit/PnL, used and free margin, margin policy, leverage, hedge/order limits, and account/terminal/EA trade permissions. This final fence applies to ordinary telemetry as well as margin-preflight frames, so a frame cannot silently combine an earlier position inventory with later account-wide financial state. The preflight calculations reuse the exact `MqlTick` embedded in that frame, and Rust binds the result to the authenticated frame sequence.
- A stop is protective only when it is strictly on the loss side of its live reference price. Zero-loss, equal-price, crossed, or profitable-side values are not accepted as confirmed protection; unresolved exposure blocks additional risk.
- Account margin policy includes initial/maintenance margin, `ACCOUNT_MARGIN_SO_CALL`, `ACCOUNT_MARGIN_SO_SO`, `ACCOUNT_MARGIN_SO_MODE`, margin mode, hedge permission, and terminal pending-order cap. One expiring native margin-preflight request may be outstanding; the terminal returns an identity-correlated result in a later frame. Directional volume-limit checks count BUY_LIMIT/BUY_STOP/BUY_STOP_LIMIT as buy exposure and the corresponding SELL types as sell exposure; partial fills contribute only their remaining order volume while filled volume appears in the positions inventory.
- `sessionSchedules`: each watched symbol's seven weekdays and all broker-reported `SymbolInfoSessionTrade` windows, indexed in broker order. Each boundary is retained as seconds from midnight in broker-server wall-clock space. A separate UTC capture instant records when the schedule was actually read; cached schedules do not pretend to have been re-observed on every heartbeat. The receiver rejects captures older than the one-hour freshness ceiling. Overnight windows remain representable; the adapter does not convert them to UTC or infer a broker timezone.
- The MQL5 adapter supports up to 8 watched symbols, 6 selected timeframes, 512 ticks per symbol per frame, and 64 closed bars per symbol/timeframe per frame. Session calendars are sent on connect/reconnect and at the configured refresh interval, not on every heartbeat, reducing recurring frame size and terminal API calls. For a series with no stored cursor, it seeds ticks from the most recent 512 and bars from the most recent 64 closed candles. Subsequent sessions resume from per-symbol/per-timeframe durable cursors returned by Rust during authentication. Configured timeframes support M1/M2/M3/M4/M5/M6/M10/M12/M15/M20/M30/H1/H2/H3/H4/H6/H8/H12/D1/W1/MN1.
- `CopyTicks` returns ticks from past to present. With `from=0` and a count it returns the last requested number of ticks; with a nonzero `from` it synchronizes from that timestamp. The EA advances its time/signature cursor only after the Rust receiver confirms the durable commit. Re-reading an inclusive millisecond boundary is expected; Rust stores a content fingerprint to suppress the same event replay. Within the same EA session, a missing prior boundary signature causes the frame to be withheld instead of skipping potentially uncommitted ticks.
- Bar recovery uses the database's last committed bar-open timestamp and `iBarShift` to resume from the first uncommitted closed bar. Backlogs are transferred oldest-first in chunks of at most 64 bars per series. If the terminal can no longer locate the exact committed bar in local history, the EA withholds the frame rather than silently jumping to the latest candle. Once per 60 seconds, it also re-reads the latest three already-committed closed bars; if the broker revises one, Rust updates the current bar and writes a revision audit row.
- The MQL5 `MqlTick` contract exposes timestamp, prices, volume, and flags, but no exchange-wide unique tick identifier. Therefore byte-for-byte indistinguishable ticks sharing the same symbol and millisecond cannot be proven to be distinct events by this adapter. They are deduplicated by content fingerprint; this limitation must be considered before using tick counts for trade-volume or microstructure inference.
- `MqlTick.time_msc` and `MqlRates.time` are preserved as reported by the broker terminal. ATOS does not silently convert broker clock/session conventions into UTC. Consumers must retain broker-server identity and avoid comparing these timestamps across brokers without explicit clock normalization.
- Bars are ingested as closed bars only. If MT5 later corrects a previously stored bar, ATOS updates the current bar and writes the prior/new content hashes to the bar-revision audit table.

## Durable commit and recovery

Market data is stored in `mt5-market-data.sqlite3` under the application's OS-managed app-data directory, separately from the paper-account ledger and research workspace. SQLite is configured for WAL mode, `synchronous=FULL`, and a bounded busy timeout.

Each frame's tick inserts, bar inserts/revisions, instrument-specification projection/revision, session-calendar projection/revision for every subscribed symbol, aggregate counters, symbol registry updates, and durable sequence receipt execute inside one `BEGIN IMMEDIATE` transaction. Session calendars use a separate current projection and append-only SHA-256 revision chain keyed by broker server, account login, and symbol. Unchanged heartbeats update observation time without creating revisions. Dataset manifests include the active session-calendar fingerprint, or an explicit unknown-calendar marker, so a changed weekly schedule changes the dataset provenance even when the stored bars do not change. The instrument specification registry is keyed by broker server, account login, and broker-native symbol. A canonical SHA-256 fingerprint suppresses unchanged heartbeat revisions; a material contract change appends an immutable history row, and reads verify the revision chain and payload fingerprints. The receiver sends an ACK only after the transaction commits. The receipt key is `(client_id, session_id, sequence)` and stores the SHA-256 of the exact frame bytes:

- A retry of a previously committed sequence with the same frame hash is treated as an exact duplicate.
- Reusing a committed sequence with different bytes is rejected.
- A sequence gap is rejected; the EA receives the durable last sequence during authentication and resumes at the next expected sequence after an application restart. The same handshake returns per-symbol tick cursors and per-symbol/timeframe bar cursors, allowing market-data recovery independently of the EA's process-local cursor arrays.
- Tick rows use a stable content fingerprint for replay suppression. Bar rows are keyed by broker server, account, symbol, timeframe, and bar-open time. Bar corrections create revision audit rows.
- Status counters are maintained transactionally; the UI does not repeatedly full-scan the entire tick table to render totals.

## Installation

1. Run the ATOS Tauri desktop application and open **MT5 Bridge**. The listener and market-data storage must both be available.
2. Select **Reveal EA pairing token** and copy the token. Hide the token after configuring the EA.
3. In MT5, use **File → Open Data Folder**, then copy `MQL5/Experts/ATOS_Bridge.mq5` into `MQL5/Experts/`.
4. Open MetaEditor, compile `ATOS_Bridge.mq5`, and confirm there are no compiler errors.
5. In MT5, open **Tools → Options → Expert Advisors** and add `127.0.0.1` to the permitted addresses for MQL5 network functions.
6. Attach **ATOS_Bridge** to a chart. Keep host `127.0.0.1`, port `47650`, paste the pairing token, and configure `InpWatchSymbols` as comma-separated broker-native symbols (maximum 8 including the primary symbol), for example `XAUUSD.a,EURUSD.a,GBPUSD.a`. Set `InpTimeframes` as a comma-separated list, for example `M1,M5,M15,H1` (maximum 6, no duplicates). `InpSessionCalendarRefreshSeconds` defaults to 300 seconds and is bounded from 30 to 3,600 seconds; the last verified schedule is reused between refreshes, while a failed refresh withholds the frame instead of silently sending stale session metadata.
7. Inspect the connection, heartbeat, account identity, quote age, durable tick/bar totals, and configured symbol coverage in ATOS. A connected status means frames have been received and committed; it does not mean live trading is enabled. Use **Inspect broker sessions** to inspect the current weekly schedule and its revision fingerprint.

Do not enable algorithmic trading for the purpose of this telemetry bridge. It does not require trade permissions to read account and market information.

## Failure behavior

- Missing OS credential-store access, occupied port, listener/storage startup error, invalid authentication, replayed nonce, malformed frame, timestamp skew, sequence discontinuity, stale quote, invalid numeric data, crossed quotes, duplicate position/order tickets, malformed pending-order states or volumes, oversized position/order lists, out-of-order ticks, unclosed bars, invalid OHLC, duplicate bar keys, or transaction failure must not be treated as valid live telemetry.
- A failed market-data transaction is not ACKed. The EA does not advance its tick/bar cursors until the exact sequence is acknowledged. It reconnects and requests the last committed sequence from Rust.
- If a configured `CopyTicks` or `CopyRates` history read fails, returns a partial chunk, or cannot locate a previously committed bar cursor, the EA withholds that frame and logs the symbol/timeframe and terminal error. If fewer than 512 ticks are returned but the current terminal tick remains newer than the candidate cursor, the EA treats this as a tick-history gap and withholds the frame. This may age the bridge heartbeat until terminal history is available again; the UI must show that state rather than fabricate a partial feed.
- When the connection is lost, the previous snapshot may remain in native memory for diagnosis but is marked stale and the UI does not present it as current connected account state.
- When a quote is older than 60 seconds, the UI marks the quote stale even if account heartbeats continue.

## Explicit release limitations

This repository environment did not contain a MetaTrader 5 terminal, MetaEditor/MQL5 compiler, Rust toolchain, or Cargo. Therefore the MQL5 adapter could not be compiled against the target terminal, the new Rust SQLite module could not be compiled or run as Rust unit tests, and the socket path could not be exercised against a real broker account here. The Node regression/contract suite verifies repository wiring and source contracts only; it does not replace Rust compilation, MetaEditor compilation, storage fault-injection, or broker integration testing.

The instrument registry currently captures the primary quote symbol only and labels the result `broker_snapshot_v1_partial`. It is not a complete margin/profit model: per-direction margin rates, expiration and start dates, all trading sessions, holiday calendars, timezone/DST normalization, and broker-specific overrides remain out of scope. The broker-native sizing calculation now consumes this record only as one input and remains explicitly limited; it is not a complete margin/profit model and must not be treated as a live execution authorization.

The adapter supports one active terminal session per desktop process. It polls tick history on a timer and uses MQL5's timestamp/price/flags fields rather than an exchange-specific tick ID. On an empty tick store, initial synchronization is deliberately bounded to the most recent 512 ticks per symbol; it does not import the full historical tick archive. Later reconnects resume from the durable timestamp cursor, subject to MT5 retaining the corresponding tick history locally or being able to download it from the trade server. Because a tick cursor has millisecond precision and no unique event ID, more than 512 indistinguishable ticks within one millisecond cannot be guaranteed to paginate without loss; tick counts must not be treated as an exchange-grade event ledger. There is no broker tick backfill service independent of a connected MT5 terminal, no automatic broker session calendar normalization, and no live order route. These remain explicit scope boundaries. The ingestion store is local SQLite; large multi-year, high-frequency histories will require measured storage/retention/partitioning work before institutional-scale deployment.

The MT5 workbench now exposes an account-wide stop-risk inventory and a broker-native risk sizing preflight. The EA uses terminal `OrderCalcProfit` for each open position/pending order; open-position risk starts at current mark so floating P/L already included in equity is not double-counted, while pending-order risk starts at activation/entry. It uses `OrderCalcMargin` plus `OrderCalcProfit` for the candidate request. Rust caps candidate risk by both the requested trade budget and remaining capacity under a 5% account-wide ceiling, blocks any unprotected/unresolved exposure, validates broker account-level and symbol trade permissions plus market/SL order flags, revalidates live quote stop distance, and checks broker stop-out thresholds plus margin/free-margin reserves. Future-dated native calculations and non-finite projection arithmetic fail closed; zero projected used margin is treated as a non-applicable percentage margin level rather than a synthetic zero-percent result. Candidate margin is conservatively added to current used margin without assuming hedged/netting relief. This is a point-in-time control calculation, not an `OrderCheck` approval, order reservation, execution authorization, or guarantee against negative balance/margin call; commission, swap, slippage and gaps remain excluded. See `MT5_BROKER_NATIVE_RISK_SIZING_ENGINE_2026-10-31.md` and `MT5_PENDING_ORDER_EXPOSURE_RECONCILIATION_2026-10-31.md`.

No live order route is implemented. Any future execution work must remain separate and include broker reconciliation, durable order intent/outbox, complete margin-aware risk checks, idempotency, permission scoping, and fault-injection tests before any live execution is considered.

## Session calendar interpretation limits

`SymbolInfoSessionTrade` reports recurring weekly session windows, not dated exchange holidays, exceptional closures, or a canonical timezone identifier. ATOS preserves the values in broker-server wall-clock space and binds the calendar fingerprint to each queried dataset manifest. Interval anomalies remain candidates, even when a weekly calendar is present: no session-aware gap is promoted to a confirmed missing candle until a separately sourced dated exception calendar and broker timezone/DST transition model are available and verified. Empty weekday session lists mean only that the terminal reported no recurring session for that weekday; they do not certify holiday coverage. The schedule is not a margin, execution-permission, or trade-safety model.
